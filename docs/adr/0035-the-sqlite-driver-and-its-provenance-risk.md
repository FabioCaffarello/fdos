# ADR-0035 — modernc.org/sqlite is the driver, and its provenance risk is accepted

## Context

[ADR-0034](0034-the-ledger-event-store.md) chose SQLite through a pure-Go driver
and deliberately left one question open:

> **which** pure-Go SQLite driver, and whether its dependency footprint passes
> the supply-chain posture. It is the first heavy dependency in the repository
> and gets the audit rather than a recommendation in passing.

The audit was performed and is recorded on
[PR #58](https://github.com/FabioCaffarello/fdos/pull/58). Both candidates were
measured in throwaway modules outside the repository.

| | `modernc.org/sqlite` v1.56.0 | `ncruces/go-sqlite3` v0.35.3 |
|---|---|---|
| Modules linked | 10 | 4 |
| Source in linked modules | ~245 MB | ~8 MB |
| Licence | BSD-3-Clause | MIT / MIT-0 |
| `CGO_ENABLED=0` | builds | builds |
| Two builds, same digest | identical | identical |
| Reachable vulnerabilities | 0 | 0 |
| Opaque blob in the linked path | **none** | **103 KB `sqlite3.dat`, embedded** |

A correction the audit produced: `ncruces/go-sqlite3` no longer runs WebAssembly
at runtime. There is no `wazero` in its graph and no `.wasm` in the build — its
`sqlite3.go` is a 4.6 MB generated Go file headed *"Code generated by wasm2go"*.
Both candidates are transpiled C, differing in route and scale rather than in
kind.

## Decision

**FDOS uses `modernc.org/sqlite`.**

The discriminator is the opaque blob. modernc's linked path is entirely Go
source the pinned toolchain compiles; `ncruces` embeds 103 KB that `file(1)`
reports as `data` into every binary. For a posture whose stated first priority is
build-input integrity, *all inputs are source* beats *fewer inputs, one of them
opaque*.

**`CGO_ENABLED=0` is pinned in the Makefile.** Both candidates build cgo-free
today and nothing stops a future version of either pulling in cgo. The pin turns
that from a silent change into a build failure, and protects the byte-
reproducibility `make repro-check` asserts.

### The risk accepted, stated rather than discovered later

**Neither candidate can be independently re-derived from upstream SQLite.**

modernc's generated files carry the full generator command line, which is
unusually good provenance — and it ends with
`-I /Users/jnml/src/modernc.org/builder/.exclude/...`. The code was generated on
the maintainer's machine against local include paths. Nobody in this repository
can regenerate it and diff it against upstream.

So `go.sum` pins **what was received**, not **that what was received corresponds
to SQLite**. That is threat #4 of `.context/docs/security.md` — *"a dependency
can alter output with no commit"* — in its subtler form: the dependency is
pinned, and verification against upstream is still impossible.

This is accepted as the cost of a pure-Go SQLite. It is not mitigated, and the
honest scope of the mitigation that does exist is small: a targeted change
between modernc versions would be visible in a source diff to anyone who looked,
where the same change inside an embedded blob would not. Nobody will read 245 MB
of generated Go, and this ADR does not pretend otherwise.

### A Postgres adapter follows rather than replaces

Recorded because it was decided at the same time and would otherwise look like
drift when it appears.

The audit found that Postgres **inverts** the finding above: `jackc/pgx/v5` is
~3 MB of hand-written Go with no generated code and no blobs, and a container
image is pinned by digest exactly as GitHub Actions already are. That is a
cleaner supply chain than any pure-Go SQLite.

It is not chosen now, for three measured reasons:

- **A networked store makes `crypto/x509` reachable.** `govulncheck` against pgx
  reports `GO-2026-5037` as reachable through TLS. It is fixable by moving the Go
  pin from 1.26.2 to 1.26.4, but the structure survives the fix: every future
  standard-library TLS advisory becomes a reachable finding, and `make verify` is
  the gate.
- **`make verify` would require a container runtime.** The toolchain today is Go
  and `make` (AGENTS.md), and a gate that needs Docker is a different developer
  contract.
- **Archival durability.** Replaying in 2031 needs a file and a Go binary with
  SQLite; with Postgres it needs a server of the right version. That argument is
  specific to a system built to answer a regulator's question years later.

`app.Store` is engine-agnostic (ADR-0034), so `libs/ledger-postgres` is additive
when a deployment needs multiple writers. Two engines also cross-check each
other: one conformance suite, two implementations.

## Consequences

### Positive

- The open item ADR-0034 left is closed with a measurement rather than a
  preference.
- `CGO_ENABLED=0` becomes enforced, so the cgo-free property stops being
  accidental.
- Everything the toolchain compiles is source.

### Negative

- **The provenance gap above is real and unmitigated.**
- ~245 MB enters the module cache of anyone importing `libs/ledger-sqlite`, and
  10 modules enter their graph, including incidental ones for a database driver
  (`go-isatty`, `go-humanize`, `google/uuid`).
- Three unreachable vulnerabilities in imported packages, against `ncruces`'s
  one. Recorded, not escalated: `govulncheck` reports zero reachable for both,
  and a scanner people learn to ignore enforces nothing.
- SQLite is single-writer, so ADR-0034's `Expectation` and knowledge-time
  monotonicity are exercised against a store that serialises anyway. The
  multi-writer case they exist for stays untested until a Postgres adapter
  exists.

### Enforcement

| Rule | Rung | Mechanism |
|------|------|-----------|
| The build stays cgo-free | 2 | `CGO_ENABLED=0` pinned in the Makefile |
| Builds stay byte-reproducible | 3 | `make repro-check` builds twice and compares digests |
| No reachable vulnerabilities | 3 | `make vuln-check` |
| The driver corresponds to upstream SQLite | **—** | **nothing. See the risk above.** |

The last row has no rung because there is no mechanism, not because the rung is
low.

## Alternatives considered

**`ncruces/go-sqlite3`.** Smaller by every measure and MIT-licensed. Lost on the
embedded 103 KB blob, which is the one input the toolchain compiles that nobody
can read.

**A cgo driver such as `mattn/go-sqlite3`.** Mature and fastest. Rejected by
ADR-0034: it makes the build depend on the host C toolchain and puts
byte-reproducibility at the mercy of a system compiler.

**PostgreSQL now.** Rejected above, with the reasons measured rather than
asserted, and explicitly deferred rather than dismissed.

**Vendoring the driver.** Would make the source reviewable in-tree and pin it
beyond `go.sum`. Rejected: it moves 245 MB of generated code into this
repository, where `make verify`, the analysers and every clone would carry it,
to buy a review nobody performs.

## Notes

The audit and its raw measurements are on PR #58. `make secrets-check` reported
no leaks and `make vuln-check` reported 6 modules free of reachable
vulnerabilities at the time it was taken.

Not covered by the audit, and the gap worth closing before trusting this with a
ledger: **crash-safety of the file format under real failure**. That is runtime
behaviour, not supply chain, and it belongs with the implementation's tests.
